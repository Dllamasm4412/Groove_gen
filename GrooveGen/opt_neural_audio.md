# Neural Audio Alternatives to MusicGen for GrooveGen Beds

## Recommendation (top of report)

**None of the surveyed neural-audio models cleanly solve the drums-baked-in problem at production quality on a free Colab T4.** The two most promising candidates both have real, disqualifying gaps for a beat-locked research system:

1. **JASCO (Meta, `facebook/jasco-chords-drums-melody-1B`)** — *partial fit, best of the neural options.* Open weights (MIT code / CC-BY-NC weights), released Jan 2025 on Hugging Face, and — uniquely among open models — takes **chords, melody, and drums as separate symbolic/audio conditioning inputs** ([HF model card](https://huggingface.co/facebook/jasco-chords-drums-400M/resolve/main/README.md?download=true), [GitHub docs](https://github.com/facebookresearch/audiocraft/blob/main/docs/JASCO.md)). You could drive genre+harmony with your own chord progressions and simply **omit the drum conditioning input**, which is architecturally the closest thing to "drumless by construction" in the open ecosystem. Caveats: 10-second generation ceiling per sample (needs stitching for bar-locked beds), 1B model VRAM footprint is untested on T4 but likely feasible given MusicGen-family sizing, no independent benchmarks yet on tempo stability, and it is a Jan-2025 research release with a thin community/support base.
2. **MusicGen-Stem (Meta/Rouard et al., arXiv:2501.01757)** — *strong concept, poor practical fit today.* This is the only model purpose-built to output **separate bass/drums/other stems autoregressively** with editable stems ([arXiv](https://arxiv.org/abs/2501.01757), [OpenReview](https://openreview.net/forum?id=3jz6yLrbF2)). Exactly the "drums as a droppable stem" capability GrooveGen needs. But as of this research, the project page states weights and code "will be released," with **no confirmed public checkpoint** — it is not currently runnable ([project page](https://simonrouard.github.io/musicgenstem/)). Track it, but do not plan around it for a paper with a passed deadline.
3. Everything else surveyed (Stable Audio Open/2.0, AudioLDM2, Mustango, Riffusion, MSG-LD, Jukebox) is **poor fit** for this specific system — mostly single-mix output with no stems, unproven genre/tempo controllability, or infeasible on a free T4. Details below.

**Bottom line for the TEI iteration:** the neural-audio ecosystem has not solved "drums-separable, genre-authentic, tempo-stable, instrumental-only, T4-feasible" as a combined package. If per-bar drum control is the paper's core contribution, the safer near-term path is almost certainly symbolic/MIDI-driven harmony + synthetic drums (outside this report's scope) rather than chasing an unreleased or unvalidated neural stem model. JASCO is worth a quick spike (a few hours) as a stretch option since it is live today and directly attacks the bed-without-drums problem; MusicGen-Stem is worth monitoring for release but not betting on.

## 2. Melody/chord-conditioned generation (bring-your-own-harmony)

- **MusicGen-Melody**: accepts an audio melody prompt (hum/whistle/clean instrument) plus text, and renders full arrangement including drums — it does **not** decouple melody-following from drum generation, so it inherits the same baked-in-drums problem GrooveGen already hit with base MusicGen ([HF docs](https://huggingface.co/docs/transformers/en/model_doc/musicgen_melody), [Meta explainer](https://medium.com/data-science/how-metas-ai-generates-music-based-on-a-reference-melody-de34acd783)). Not a fix, just a different prompt path into the same failure mode.
- **JASCO** is the one model in this survey that lets you supply chords AND melody as independent conditioning channels *while separately toggling drum conditioning off* — this is the closest match to "we drive genre+harmony ourselves and skip drums" ([JASCO docs](https://github.com/facebookresearch/audiocraft/blob/main/docs/JASCO.md)). Untested by us for salsa/r&b authenticity or tempo grid-lock; a same-day Colab spike (generate a handful of 10s clips per genre with drums conditioning omitted, measure the same percussive/harmonic RMS ratio used for MusicGen) would settle this quickly and cheaply.
- **Stable Audio (audio-to-audio / ControlNet variants)**: `stable-audio-controlnet` (community project) adds ControlNet-style conditioning on top of Stable Audio Open, usable with ~16GB VRAM adapters ([GitHub](https://github.com/EmilianPostolache/stable-audio-controlnet)), but this is single-mix output — no drum/melody stem split, and it's an unofficial, work-in-progress fork ("code is provided as-is").

## 3. Practicality on Colab T4 (16GB)

- **JASCO 400M/1B**: sized like musicgen-small/medium; AudioCraft install path is the same PyTorch/transformers stack GrooveGen already has working, so Python 3.12 risk should be similar to what was already solved for MusicGen. 10-second-per-clip ceiling means bar-locked beds need chunk-and-stitch, adding complexity and potential tempo drift at seams.
- **Stable Audio Open**: confirmed T4-compatible (~6-12GB VRAM), fast per official benchmarks (8 steps/sec on RTX-3090-class cards), but has no drum-separable output and a 47s cap — a dead end for the actual ask even though it's the easiest to run.
- **AudioLDM2**: runs on CUDA but diffusion sampling (200 steps recommended) will be slow on a T4 relative to MusicGen's autoregressive decode; RAM notes in official docs (~20GB for some modes) are a yellow flag for Colab's default RAM tier.
- **MSG-LD / Multi-Track MusicLDM**: research-grade, 16kHz sample rate (below production quality), narrow Slakh-trained vocabulary (no salsa/r&b), and the MSG-LD paper itself flags weak unconditioned drum coherence — this undercuts the one thing we'd want it for.
- **Jukebox**: ruled out — VRAM and runtime make it impractical even as an experiment; community consensus is Colab is "problematic" for it even with workarounds.
- **Riffusion**: cheap to run but not built for coherent, bar-aligned generation; treat as a novelty, not a research pipeline component.
- **MusicGen-Stem**: moot until weights ship.

## 4. The vocals constraint

- MusicGen family (including MusicGen-Stem, JASCO): explicitly trained on vocal-stripped/licensed instrumental data via HT-Demucs preprocessing — reliably instrumental ([Open Laboratory model card](https://openlaboratory.com/models/musicgen/)).
- Stable Audio Open: not marketed as a vocal generator; SFX/music focus makes stray vocals unlikely but not contractually guaranteed.
- AudioLDM2: the general checkpoint is a unified text-to-audio/**speech**/music model, so vocal leakage risk is real depending on prompt; the `audioldm2-music` checkpoint is the safer choice if this path is pursued.
- Jukebox: the `5b_lyrics` variant actively generates vocals; only the non-lyrics checkpoints avoid this, and even those were trained on a vocal-heavy corpus (raised risk of stylistic vocal-like artifacts).
- Riffusion, Mustango, MSG-LD: no explicit vocal-avoidance guarantees; risk is dataset-dependent and unverified.
