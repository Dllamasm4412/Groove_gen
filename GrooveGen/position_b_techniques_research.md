# Position B: Tempo-Control Techniques for Neural Music Generation
## Research for a closed-loop biofeedback music system requiring exact BPM lock and downbeat-grid alignment

**Context:** Current MusicGen output wanders ~127ms off a target tempo grid. This system needs generated audio that locks to an exact BPM and known downbeat grid so symbolic drums can be aligned without wander, in a real-time closed-loop biofeedback setting.

---

## Executive framing: the core problem

Tempo/beat wander in autoregressive and diffusion text-to-music models is fundamentally a **conditioning-precision problem**: none of the mainstream generative backbones (MusicGen, MusicLM, AudioLDM, Stable Audio) were trained with a hard, sample-accurate metrical grid as a first-class conditioning signal — tempo is either a fuzzy text token ("120 BPM") or an emergent property of the training distribution. Getting from "approximately on tempo" to "locked to an exact BPM and downbeat grid within ms tolerance" requires either (a) a model *trained* with a precise time-varying rhythm signal, (b) inference-time optimization/guidance toward a precise target, or (c) accepting approximate generation and enforcing the grid with **deterministic DSP after the fact**. Below, each family of techniques is evaluated on this axis.

---

## 1. Beat/Tempo Conditioning Methods for Audio Generation (trained-in control)

### 1.1 Music ControlNet (Wu, Donahue, Watanabe, Bryan — Adobe/CMU, 2023)
- **What it is:** A diffusion-based (spectrogram) text-to-music model that adapts the image-domain ControlNet scheme to add time-varying controls — melody, dynamics, and **rhythm** (beat/downbeat) — on top of a pretrained backbone, via a cloned/fine-tuned adaptor branch. Controls can be fully or partially specified in time. [arXiv:2311.07069](https://arxiv.org/abs/2311.07069)
- **Precision:** Rhythm control signal is a soft-onset beat/downbeat one-hot-like array with a tolerance kernel (order ~tens of ms), not a hard sample-accurate signal — this is **approximate, not exact** tempo lock. The paper reports Music ControlNet beats melody control accuracy vs. MusicGen (49% more faithful) with far fewer parameters (41M vs 1.5B), but does not report tempo error in ms.
- **Code/compute:** Research-only release from Adobe/CMU; no official public inference repo has been widely distributed as of this writing (demo site + paper only). Training required (diffusion U-Net, moderate compute — far cheaper than training MusicGen from scratch, but still non-trivial GPU-hours).
- **Verdict:** Promising *architecture pattern* (ControlNet-style time-varying rhythm injection) but **not a drop-in solution**: no official runnable checkpoint verified, and reported control is class-level rhythm adherence, not millisecond-exact grid lock. Would need re-implementation and re-training with a stricter rhythm signal (e.g., a hard click-track channel) to hit exact BPM.

### 1.2 JASCO — Joint Audio and Symbolic Conditioning (Meta, 2024)
- **What it is:** A Flow-Matching text-to-music model supporting simultaneous symbolic (chords) and audio-based (melody, drums) time-aligned conditioning, using information-bottleneck + temporal-blurring layers. [arXiv:2406.10970](https://arxiv.org/html/2406.10970v1); official code and docs in Meta's Audiocraft repo: [github.com/facebookresearch/audiocraft/blob/main/docs/JASCO.md](https://github.com/facebookresearch/audiocraft/blob/main/docs/JASCO.md)
- **Precision:** JASCO extracts drum conditioning via a source-separation network and encodes it as a temporally-aligned low-dimensional signal — this gives *drum-pattern* conditioning (which implicitly carries tempo/rhythm), but it is trained with "temporal blurring," meaning the model is explicitly regularized to **tolerate timing slop** rather than lock to a rigid grid. It is a text-to-music model, not a metronome-exact renderer.
- **Compute/code:** Real, runnable, open-source (Apache/MIT-style Audiocraft license), 7x faster inference than autoregressive MusicGen (flow matching), moderate GPU requirement for inference (single consumer/prosumer GPU feasible), but training requires the source-separation preprocessing pipeline and non-trivial data curation.
- **Verdict:** Best "runs today" option among trained conditioning models because it ships in Audiocraft with real code. But by design it blurs precise timing to stay musically natural — **approximate tempo control**, not exact-lock. Likely needs its drum/audio-conditioning branch fed a literal click/metronome signal (not naturalistic drum audio) to push toward tighter lock; untested whether temporal blurring can be disabled without destabilizing training.

### 1.3 MusicGen chroma/melody conditioning (Meta, native)
- **What it is:** MusicGen's built-in `generate_with_chroma` conditions on a binarized chromagram extracted from a reference melody; there's also `generate_continuation`. [Hugging Face MusicGen docs](https://huggingface.co/docs/transformers/model_doc/musicgen); [Audiocraft repo](https://github.com/facebookresearch/audiocraft)
- **Precision:** Chroma conditioning controls pitch-class content, **not** rhythm or tempo. Tempo in vanilla MusicGen is only steered via the text prompt (e.g., "120 BPM") — this is the mechanism the project has already found to wander ~127ms. No architectural component in stock MusicGen enforces a hard beat grid.
- **Verdict:** **Confirmed inadequate on its own** — consistent with the project's own observed 127ms wander. Chroma conditioning is orthogonal to the tempo problem; not a fix.

### 1.4 MusiConGen (Lan, Hsiao, Cheng, Yang — ISMIR 2024)
- **What it is:** Fine-tunes pretrained MusicGen with an efficient, consumer-GPU-friendly mechanism that adds **automatically-extracted rhythm (beat + downbeat) and chords** as temporal conditioning, usable with either audio-extracted or **user-defined symbolic BPM** at inference. [arXiv:2407.15060](https://arxiv.org/html/2407.15060v1); **official open-source code + checkpoints**: [github.com/Cyan0731/MusiConGen](https://github.com/YatingMusic/MusiConGen), replicate/cog wrapper at [github.com/sakemin/cog-MusiConGen](https://github.com/sakemin/cog-MusiConGen)
- **Precision:** Encodes beat and downbeat as one-hot frame-wise arrays with an explicit **70ms soft tolerance kernel** baked into training — i.e., the model is *designed* to accept ~70ms of timing slack, which is roughly half of the project's current 127ms problem but still not an exact lock. Directly accepts a symbolic BPM value as a conditioning input (not just text), which is a meaningfully tighter interface than prompt-string tempo.
- **Compute:** Fine-tuning is explicitly designed to run on **consumer-grade GPUs** — much cheaper than full MusicGen retraining. Inference cost is close to base MusicGen (autoregressive, ~50 steps/sec of audio).
- **Verdict:** **Most actionable trained-conditioning technique found.** Real code, real checkpoints, explicit symbolic BPM input, and beat/downbeat conditioning purpose-built to reduce exactly this failure mode. Still bounded by a ~70ms design tolerance and is autoregressive-transformer based (sampling drift can still accumulate over long generations). Recommended as a **primary candidate**, ideally combined with post-hoc quantization (Section 3) to close the remaining gap to sample-accurate.

### 1.5 Mustango (MuNet) — chord/beat/key/tempo diffusion (2023)
- **What it is:** A text-to-music latent diffusion model with a domain-knowledge-informed UNet (MuNet) conditioned on tempo (BPM), beats, key, and chords, estimated from training audio and predicted at inference by dedicated transformer models. [arXiv:2311.08355](https://arxiv.org/html/2311.08355v3)
- **Precision:** Evaluated with explicit "Beat" and "Tempo" controllability metrics; the paper reports Mustango performs comparably to or slightly behind MusicGen on tempo/beat metrics in their benchmark — i.e., **not clearly better** than MusicGen at exact tempo, despite explicit tempo conditioning. Inference is diffusion-based (200 steps), ~76 sec for a 10-sec clip on a V100 — far from real-time.
- **Verdict:** Interesting for explicit tempo-as-conditioning-variable design, but empirically doesn't outperform MusicGen on tempo accuracy and is too slow for real-time use as-is. Lower priority.

### 1.6 MuseControlLite (2025)
- **What it is:** A lightweight (85M param) decoupled cross-attention adapter with rotary positional embeddings for time-varying control (melody, dynamics, beat) on Stable Audio Open's DiT backbone — positioned as a cheaper, more parameter-efficient alternative to ControlNet-style branches (85M vs 572M params). [arXiv:2506.18729](https://arxiv.org/html/2506.18729v1); code promised at [musecontrollite.github.io/web](https://musecontrollite.github.io/web/) ("code will be released soon" as of paper publication)
- **Precision:** Melody control accuracy improves from 56.6% to 61.1% with RoPE — useful signal that positional embeddings matter for time-varying control, but again this is accuracy/adherence, not ms-level tempo lock, and beat/rhythm-specific numbers aren't the headline metric.
- **Verdict:** Architecturally interesting (cheap fine-tuning cost), but code availability was uncertain/pending at last check — **verify before depending on it**.

### 1.7 Stable Audio timing conditioning
- **What it is:** Stable Audio's diffusion model is conditioned on `seconds_start`/`seconds_total` timing embeddings controlling clip length/structure, and text prompts can include BPM (e.g., "128 BPM tech house drum loop"). [Stability AI research post](https://stability.ai/research/stable-audio-efficient-timing-latent-diffusion); [arXiv:2402.04825](https://arxiv.org/pdf/2402.04825)
- **Precision:** Timing conditioning controls **duration/structure**, not beat-grid phase. BPM is only expressed via text prompt — same weak mechanism MusicGen already uses. Community tools like [RC-stable-audio-tools](https://github.com/RoyalCities/RC-stable-audio-tools) add a BPM/Bar selector UI that auto-fills the prompt, but this is still text-level steering, not a hard constraint. Stable Audio 3.0 marketing explicitly states it "doesn't guarantee BPM accuracy numerically" ([MindStudio review](https://www.mindstudio.ai/blog/stable-audio-3-open-weight-music-generation)).
- **Verdict:** No better than MusicGen for exact tempo; useful only for duration control.

**Section 1 summary verdict:** Trained-in conditioning methods (Music ControlNet, JASCO, MusiConGen, Mustango, MuseControlLite) all improve rhythm *adherence* over vanilla MusicGen, but every one that reports a number designs in a soft tolerance window (order 70ms) rather than sample-exact lock, because the models are trained to generate *naturalistic* human-like timing, not metronomic timing. **None of these alone will deliver an exact-BPM, zero-wander grid.** MusiConGen is the strongest practical candidate due to open code + symbolic BPM input + explicit rhythm conditioning designed for exactly this problem.

## 2. Inference-Time Control Without Retraining

### 2.1 DITTO — Diffusion Inference-Time T-Optimization (Novack, McAuley, Berg-Kirkpatrick, Bryan — ICML 2024)
- **What it is:** A general-purpose, **training-free** framework that optimizes the *initial noise latent* of a pretrained diffusion TTM model against any differentiable feature-matching loss (e.g., match a target intensity curve, melody, or structure), via gradient checkpointing for memory efficiency. Demonstrated on inpainting, outpainting, looping, intensity, melody, and structure control. [arXiv:2401.12179](https://arxiv.org/html/2401.12179v2); [project page](https://ditto-music.github.io/web/); [ICML slides](https://icml.cc/media/icml-2024/Slides/35440_cbIXAu2.pdf)
- **Precision:** DITTO optimizes toward *any differentiable* target, so in principle a **beat/tempo-tracking loss** (e.g., match generated audio's onset envelope or a differentiable tempogram to a target click track) could be added as a new task not explicitly benchmarked in the paper. The paper's demonstrated controls (melody, intensity, structure) show strong state-of-the-art adherence versus guidance and other optimization baselines — this suggests a bespoke tempo-matching loss could plausibly get much closer to exact than trained conditioning, **but this specific tempo application is not in the published results** and would require custom loss engineering and validation.
- **Compute cost:** The key drawback: DITTO is reported to be **over 10x slower than real-time** — each generation requires an iterative optimization loop backpropagating through the diffusion sampler. This makes it unsuitable for a live, real-time biofeedback loop without acceleration.
- **Code:** Research paper + demo site; a runnable open-source release specifically for DITTO does not appear to be officially published/maintained (only sound examples at the project page) — **would need to reimplement algorithm 1 from the paper**.
- **Verdict:** Best *precision-per-effort* inference-time technique conceptually, but (a) too slow for live use out of the box, (b) exact tempo-lock loss function not proven in literature, (c) no ready-to-run public codebase. Good candidate for **offline pre-generation** of a bed loop (generate once with DITTO's tempo-matching loss, then loop it live) rather than live per-request generation.

### 2.2 DITTO-2 — Distilled DITTO (Novack et al., 2024)
- **What it is:** Speeds up DITTO 10-20x by (1) distilling the diffusion model via consistency/consistency-trajectory distillation for fast 1-step sampling, (2) running the expensive inference-time optimization against the cheap distilled model, then (3) doing a final multi-step high-quality decode. [arXiv:2405.20289](https://arxiv.org/abs/2405.20289); [project page/audio examples](https://ditto-music.github.io/ditto2/)
- **Precision:** Same optimization paradigm as DITTO — control adherence reportedly *improves*, not just speed. Still no published tempo-specific benchmark, but the mechanism generalizes.
- **Compute:** With the 10-20x speedup, DITTO-2 claims **faster-than-real-time** generation (e.g., ~230ms for 32s of mono audio reported by third-party summary, [EmergentMind](https://www.emergentmind.com/topics/text-to-music-generation-ttm)) — this crosses into practically deployable territory for a live system, assuming the distillation step is done for whatever backbone is used.
- **Code:** Same situation as DITTO — no widely distributed official public repo found; would require reimplementation using the paper's distillation recipe on top of an open diffusion TTM backbone (e.g., Stable Audio Open).
- **Verdict:** **Most promising inference-time-control technique for this project if a custom tempo-matching loss is engineered and validated**, because it's the only technique in this category claiming faster-than-real-time speed while retaining/improving control adherence. Requires nontrivial engineering (train a distilled model, implement/validate the tempo loss) — this is a research/engineering project in itself, not a plug-in.

### 2.3 Classifier Guidance
- **What it is:** A noise-conditioned classifier's gradient is used to steer the diffusion sampling trajectory toward a desired class/attribute at each denoising step. [Survey: arXiv:2506.08457](https://arxiv.org/html/2506.08457v1); Apple's guidance framework for music production applies reconstruction/classification losses at sampling time for continuation, inpainting, and style transfer. [Apple ML Research](https://machinelearning.apple.com/research/controllable-music)
- **Precision:** Classifier guidance is good for **class-level or embedding-level attributes** (e.g., "this sounds energetic," "this matches this reference clip's aesthetic") but is a poor fit for **exact scalar/periodic targets** like "126.7ms period, phase-locked to t=0." A tempo classifier's gradient would push toward "tempo-ish" regions of latent space, not enforce an exact period — same class of problem as text-based tempo prompting, just smoother.
- **Compute:** Adds one classifier forward+backward pass per diffusion step — moderate overhead, much cheaper than DITTO's full optimization loop, but still slower than an unguided pass.
- **Verdict:** **Not suited for exact tempo lock** — better suited to global mood/style attributes. DITTO's paper explicitly notes prior guidance-based methods "particularly struggle" compared to DITTO for the outpainting/coherence tasks tested.

### 2.4 MultiDiffusion
- **What it is:** A training-free framework that fuses multiple diffusion generation paths bound by shared constraints, originally for panoramic/region-controlled image generation. [Project/paper](https://multidiffusion.github.io/paper.pdf)
- **Relevance to tempo:** Not designed for audio or tempo; DITTO's own paper cites MultiDiffusion as a **baseline for outpainting that "struggles to maintain long-form coherence and local smoothing"** when adapted to music — i.e., it's been tried adjacent to this exact problem (long-form music generation) and underperformed DITTO.
- **Verdict:** Not recommended; superseded by DITTO/DITTO-2 for the audio continuation use case, and has no native tempo-locking mechanism.

### 2.5 MusicRFM — Recursive Feature Machine steering (2025, OpenReview)
- **What it is:** Trains lightweight RFM probes on MusicGen's internal activations to find interpretable "concept directions" (including tempo), then injects them at inference via forward hooks for real-time, per-step-optimization-free control, including **dynamic time-varying schedules** and **joint control of notes and tempo**. [OpenReview PDF](https://openreview.net/pdf/25c38a1b772e91855c879b80290cbe969af63452.pdf)
- **Precision:** Explicitly claims tempo as one of the controllable concepts, and — critically — requires **no per-step optimization at inference**, unlike DITTO, which is a major practical advantage for real-time use. However this is a very new (unreleased-as-verified) result; no independent tempo-error benchmark (ms) was found, and code availability is unconfirmed.
- **Verdict:** **Worth monitoring closely** — architecturally the most real-time-friendly inference-time technique found (activation steering, not optimization), and it's the only one explicitly targeting joint "notes and tempo" control on MusicGen specifically. Not yet mature enough to rely on without independent verification of exact-tempo accuracy and code availability.

**Section 2 summary verdict:** Inference-time methods trade retraining cost for either (a) heavy per-generation compute (DITTO: >10x slower than real-time) or (b) reduced precision for exact periodic targets (classifier guidance, MultiDiffusion). DITTO-2 is the standout if the team is willing to engineer a custom tempo-matching loss and validate it — no one has published that this hits exact tempo, but the mechanism (differentiable feature matching against initial noise) is the most principled fit for a hard numeric target of any technique surveyed. MusicRFM is an emerging alternative that avoids the speed penalty entirely if it proves real.

## 3. Post-Hoc Tempo Stabilization (deterministic DSP — the "safe fallback")

This category **does not depend on model internals at all** and is the only family of techniques that can *guarantee* exact tempo/grid lock, at the cost of audio quality/naturalness tradeoffs.

### 3.1 Beat tracking + quantization pipelines
- **madmom** — mature Python MIR library with state-of-the-art offline beat/downbeat/tempo tracking (RNN + DBN); has a streaming/online extension pattern used by third parties (e.g., [Sma1033/Realtime-beat-tracking](https://github.com/Sma1033/Realtime-beat-tracking)). [arXiv:1605.07008](https://arxiv.org/abs/1605.07008); [GitHub](https://github.com/CPJKU/madmom)
- **BeatNet** — real-time (streaming mode from live mic input), causal CRNN + two-stage cascade particle filtering for joint beat/downbeat/tempo/meter tracking; theoretical latency = STFT hop size (~20ms in BeatNet+); F1 tolerance windows of 70ms/200ms are standard in this literature. [arXiv:2108.03576](https://arxiv.org/abs/2108.03576); [GitHub - mjhydri/BeatNet](https://github.com/mjhydri/BeatNet); BeatNet+ improvement: [Transactions of ISMIR](https://transactions.ismir.net/articles/10.5334/tismir.198)
- **aubio** — lightweight real-time C/Python library for onset detection, pitch, and beat tapping, widely used in embedded/live contexts. [aubio.org](https://aubio.org/)
- **Rhythm quantization models** — transformer-based rhythm quantization (given a-priori beat/metronome positions) can snap performance timing to a metrical grid with 97.3% onset F1 on ASAP, explicitly noting that having ground-truth/metronome beat info **eliminates uncertainty in beat estimation**. [arXiv:2508.19262](https://arxiv.org/html/2508.19262v1)
- **Precision:** Because this project *already knows* the target BPM and downbeat grid (it's a design parameter, not something to infer), the hard part — beat estimation — is unnecessary. The project doesn't need to detect tempo; it needs to **impose** tempo, which is strictly easier. This shifts the task from "beat tracking" to "time-stretching to a known target," which is precisely rubberband/phase-vocoder territory (3.2).
- **Verdict:** Beat-tracking-based approaches are the wrong tool if the target grid is already known — they're built for *inferring* unknown tempo/beats from audio, not *imposing* a known one. Useful only as a QA/verification step (confirm generated audio is actually on-grid after correction).

### 3.2 Rubber Band / phase vocoder time-stretching to a known target
- **Rubber Band Library** — mature C++ time-stretching/pitch-shifting library; independently adjusts tempo and pitch; used broadly in DAWs. It's a **block-based phase vocoder with phase resets on percussive transients** and an adaptive stretch ratio, plus a "lamination" method for vertical phase coherence — specifically engineered to reduce the smearing artifacts of naive phase vocoding. [breakfastquay.com/rubberband/technical](https://breakfastquay.com/rubberband/technical.html); [GitHub](https://github.com/jlank/rubberband)
- **librosa.phase_vocoder** — reference/pedagogical implementation; librosa's own docs recommend Rubber Band for anything beyond toy use because the built-in implementation "makes no attempt to handle transients" and "is likely to produce many audible artifacts." [librosa docs](https://librosa.org/doc/0.11.0/generated/librosa.phase_vocoder.html)
- **Precision:** This is the **only technique surveyed that can deliver deterministic, exact, sample-accurate tempo lock** — given a measured actual tempo (via any offline tempo estimate, or simply by design since the generator's nominal BPM is known/set) and a target BPM, the stretch ratio is an exact arithmetic calculation (`target_bpm / actual_bpm`), and Rubber Band applies it deterministically.
- **Quality tradeoffs:** Time-stretching is not free — larger stretch ratios introduce audible artifacts (smearing, "phasiness," pre-echo on transients) especially on percussive/drum content. Since the MusicGen wander is only ~127ms over some clip duration (i.e., a *very small* relative stretch ratio, likely well under 1%), this is a **best-case scenario for phase vocoding** — sub-1% time stretch is generally close to inaudible for most program material, especially non-percussive beds. This is a strong argument for accepting approximate generation + correcting with Rubber Band rather than chasing exact-tempo generation.
- **Compute:** Extremely cheap (real-time-capable DSP, runs on CPU, no GPU needed), and it is a mature, battle-tested, off-the-shelf dependency (also wrapped in `pyrubberband` for Python, and bundled in ffmpeg via `librubberband`).
- **Verdict:** **Highest-confidence, lowest-risk technique in this entire survey.** Given the specific numbers in this project (small ~127ms drift), a beat-tracked-or-known actual tempo + Rubber Band correction to the exact target BPM is very likely to solve the stated problem with minimal quality cost, and it requires zero model retraining, no GPU, and mature open-source tooling. **Recommended as the backbone of the solution**, potentially combined with a trained-conditioning model (Section 1, e.g. MusiConGen) to minimize the amount of correction needed (smaller stretch ratio → less artifacting) and/or DITTO-style inference-time steering for the bed's "musical" content while Rubber Band guarantees the hard grid constraint.

### 3.3 Differentiable DSP (DDSP)
- **What it is:** Magenta's DDSP framework decomposes audio into interpretable control parameters (pitch/F0, loudness, latent timbre residual) driving classical synthesizers (harmonic oscillator + filtered noise) end-to-end differentiably; real-time C++/Max implementations exist (e.g., [Caillon's real-time DDSP](https://caillonantoine.github.io/2021/03/01/ddsp.html), [DDSP-SVC](https://github.com/yxlllc/DDSP-SVC)). [Magenta GitHub](https://github.com/magenta/ddsp); [QMUL DDSP review](https://comma.eecs.qmul.ac.uk/assets/pdf/Hayes_DDSP_Review.pdf)
- **Precision/fit:** DDSP is fundamentally a **monophonic, per-instrument timbre/pitch/loudness control** technology (originally demonstrated on solo violin, etc.) — it is not designed for polyphonic mixed-genre "beds" like MusicGen output, and it doesn't have a native concept of "beat grid." Its differentiable oscillators do offer phase continuity, which is architecturally elegant, but repurposing DDSP for tempo-locking a full mix would require essentially resynthesizing the whole texture through a DDSP decoder — a nontrivial re-engineering effort, and current real-time DDSP implementations target single-instrument timbre transfer, not tempo correction of complex polyphonic material.
- **Verdict:** **Not a good fit** for this project's actual need (tempo-locking pre-generated polyphonic beds). Interesting technology, wrong scope. Rubber Band directly solves the stated problem with far less engineering.

## 4. Continuation / Seamless Looping for Indefinite Beds

### 4.1 DITTO's native looping/outpainting mode
- DITTO explicitly introduces **looping as a new inference-time task**: it overlaps two edge regions of the output analogous to inpainting/outpainting so the extended region seamlessly transitions back to the clip's beginning, avoiding the "hard seam" failure mode of baseline outpainting (MultiDiffusion, Guidance Gradients). Subjective listening tests show DITTO is strongly preferred over FreeDoM and Music ControlNet baselines for outpainting/looping. [arXiv:2401.12179](https://arxiv.org/html/2401.12179v2)
- **Verdict:** Good technique conceptually, but inherits DITTO's real-time speed problem (Section 2.1) unless run through the DITTO-2 distillation pipeline. Ideal for **precomputing** a small library of perfectly seamless loop beds offline, rather than looping live.

### 4.2 LoopGen — training-free loopable generation for non-autoregressive models (2025)
- **What it is:** Modifies MAGNeT's (Meta's non-autoregressive parallel-decoding music model) iterative inference with **circular padding** so the model attends to the clip's beginning while generating its ending, creating natural "bridging tokens." Works both to generate new loopable segments from scratch or to refine an existing sample's tail. Includes a **beat-aware constraint aligning total loop length to musical bars**. Reports 55% improvement in seam-perplexity and 70% better mean listening-test ratings vs. baselines — with **no additional training or data required**. [arXiv:2504.04466](https://www.arxiv.org/pdf/2504.04466.pdf)
- **Precision/fit:** This is the most directly relevant "seamless bed" technique found — it's inference-only (cheap), explicitly bar/beat-aware (aligns with the project's downbeat-grid requirement), and built for exactly the "extend a bed indefinitely without seams" use case. It requires MAGNeT specifically (non-autoregressive architecture), not MusicGen (autoregressive) — a backbone change/addition would be needed.
- **Verdict:** **Strong candidate technique**, likely the best fit in this section given the explicit beat-awareness and zero training cost. Should be evaluated directly against the project's current MusicGen-based pipeline; may argue for adopting MAGNeT as (or alongside) the generation backbone specifically for the looping stage.

### 4.3 ACE-Step Audio Outpaint (commercial/2025)
- Diffusion-based bidirectional outpainting (extend before/after existing audio) built on the ACE-Step foundation model, explicitly claims to preserve "rhythm, tone, emotion, and production style" and blends via crossfade at the seam. [WaveSpeedAI blog](https://wavespeed.ai/blog/posts/introducing-wavespeed-ai-ace-step-audio-outpaint-on-wavespeedai/); [RunComfy](https://www.runcomfy.com/models/acestep-ai/ace-step/audio-outpaint)
- **Verdict:** Commercial/hosted API, not obviously self-hostable at the same quality; treat as a product to trial, not a research technique to reimplement. Lower priority for a research-grade closed-loop pipeline needing tight control and low external-API latency.

### 4.4 Live Music Diffusion Models (LMDMs) — streaming block-diffusion with KV caching (2026)
- **What it is:** A very recent technique that repurposes block-wise outpainting diffusion into a genuinely streaming architecture via noise-wise/time-wise KV caching, reducing latency into the **~30ms regime** on a **consumer gaming laptop**, and introduces "ARC-Forcing" post-training to prevent error accumulation over long (minute-scale) generations without RL. Demonstrated as a live "generative delay" effect for real musicians. [arXiv (2605.22717)](https://arxiv.org/html/2605.22717v1); [demo video](https://www.youtube.com/watch?v=y2CmJZ3lyw4)
- **Relevance:** This is architecturally the closest published system to what the biofeedback project needs structurally — a live, continuously-running, low-latency streaming generator that extends context indefinitely, on affordable hardware, without RL-based post-training complexity. It is very new (2026) and framed for musician-collaboration/jamming rather than biofeedback specifically, and does not itself claim exact tempo lock — it inherits whatever tempo behavior its base diffusion backbone has.
- **Verdict:** **Highest architectural relevance for the "indefinite live bed" requirement**, and should be tracked closely — but it's bleeding-edge (no long track record, unclear if code is public) and would still need to be paired with a tempo-locking layer (Section 1 conditioning and/or Section 3 DSP correction) since it doesn't solve exact-BPM by itself.

### 4.5 Native MusicGen continuation
- Base MusicGen supports `generate_continuation` (feed prior audio tokens, predict the next chunk) — this is what the project is presumably already using. [Audiocraft continuation code example](https://github.com/stjordanis/MusicGen-Continuation); [MusicGen HF docs](https://huggingface.co/docs/transformers/v4.43.2/en/model_doc/musicgen) note generation is capped to 30 seconds per call including any prompt audio, requiring **chunked continuation calls** to go longer — each chunk boundary is a potential source of the observed tempo/timing drift, since each new autoregressive call re-derives its own sense of tempo from context rather than being locked to a persistent absolute clock.
- **Verdict:** This chunking behavior is a plausible **root cause contributor** to the reported 127ms wander — worth instrumenting directly. Switching to LoopGen-style circular-aware generation, MusiConGen's explicit BPM conditioning per chunk, or DITTO-2 looping/outpainting could all directly address this specific mechanism.

**Section 4 summary verdict:** LoopGen (bar/beat-aware, zero-cost, works today conceptually) and LMDMs (cutting-edge streaming architecture) are the two standout looping techniques. Neither alone guarantees exact BPM — they solve the "no seams, extend indefinitely" problem, which is a distinct but complementary requirement to tempo-lock (Sections 1–3).

## 5. Published Closed-Loop / Biofeedback Music Generation Systems

### 5.1 MindMelody — closed-loop EEG-driven personalized music intervention (2026)
- **Generation engine:** **MusicGen-medium (1.5B)** used as a frozen pretrained backbone; the novel contribution is a lightweight **Hierarchical EEG Controller** (global affect prefix + local temporal control branch) trained on top, translating EEG-derived valence/arousal states and a Qwen2.5-7B-Instruct RAG planner's structured intervention plan into MusicGen conditioning. [arXiv:2605.01235](https://arxiv.org/html/2605.01235v1)
- **Real-time handling:** Operates in 10-second generation windows, with 4-second/2-second-overlap EEG segmentation; the intervention planner outputs a **target tempo** parameter, though the paper doesn't publish exact BPM error/ms or end-to-end latency numbers.
- **Relevance:** This is the closest published architecture to the project's own approach (physiological signal → controller → MusicGen), which validates the general design pattern but also means **MindMelody has not solved the tempo-lock problem either** — it doesn't report tempo precision, and its short 10-second windows sidestep (rather than solve) long-form drift.
- **Verdict:** Useful as an architectural precedent and comparison point, not as a source of a tempo-lock solution.

### 5.2 AffectMachine-Pop / AffectMachine-Classical — real-time symbolic affective music (Agres, Dash, Chua, Ehrlich et al.)
- **Generation engine:** A **rule-based/symbolic expert system**, explicitly *not* a neural generative model — hand-composed rhythmic pattern banks (bass, guitar, percussion), a probabilistic chord-progression matrix, and voice-leading logic, manually tuned by expert musicians. [AffectMachine-Pop, arXiv:2506.08200](https://arxiv.org/html/2506.08200v1); [AffectMachine-Classical, Frontiers in Psychology](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2023.1158172/full)
- **Real-time/tempo handling:** Tempo is **directly and deterministically computed** from the arousal signal via a logarithmic mapping into range [36, 130] BPM — because the system is symbolic (MIDI-like note events with explicit onset/duration), tempo is **exact by construction**, with no wander possible; new rhythmic patterns are swapped in at fixed bar boundaries (every bar or every 8 bars) rather than mid-phrase, preserving grid alignment.
- **Verdict:** **This is the key structural insight from the literature**: the only systems that achieve exact, wander-free tempo lock in this survey are **symbolic** (rule-based or MIDI-generating), because tempo is a parameter of the sequencer/clock, not an emergent property learned from waveform statistics. This strongly supports a **hybrid architecture**: use a symbolic/MIDI-precise clock and drum grid (as this project already plans) and treat the neural audio generator (MusicGen or successor) purely as a **timbral bed/texture layer**, decoupled from the hard clock — reconciled via the DSP correction of Section 3, not by expecting the neural model to self-discipline to the grid.

### 5.3 HEARTBEATS — cadence/heart-rate-synchronized running music (NIME 2020)
- **Generation engine:** Generative music production techniques (second-order Markov model for rhythmic/melodic feature generation), driven by heart-rate or accelerometer/cadence data from a wearable BLE sensor. [NIME 2020 paper](https://www.nime.org/proceedings/2020/nime2020_paper102.pdf)
- **Real-time handling:** Explicitly notes: **"Latency is minimal but transformations occur at bar breaks,"** giving the impression of instantaneous response at all but very slow tempos — i.e., they intentionally quantize *when* changes take effect to bar boundaries to preserve rhythmic integrity, rather than allowing continuous/instant parameter changes that could create seams or timing artifacts.
- **Verdict:** Another confirmation of the "commit changes only at bar/beat boundaries" pattern as a robust practical strategy for any closed-loop biofeedback music system — directly transferable design guidance regardless of which generation engine is used.

### 5.4 Coupling the Heart to Musical Machines (PPG NIME controller, 2025)
- **What it is:** A photoplethysmogram (PPG)-based controller using heart rate as a continuous 1D control parameter to transform sound qualities in real time over Bluetooth, in a New Interfaces for Musical Expression (NIME) context. [arXiv:2505.03073](https://arxiv.org/abs/2505.03073v1)
- **Relevance:** Demonstrates real-time HR→sound-parameter mapping but at the level of live signal-processing/synthesis control (timbral transformation), not generative composition with a beat grid — a lower-level precedent than MindMelody or AffectMachine, useful mainly for validating BLE/PPG signal-chain latency expectations.

### 5.5 Other relevant precedents found
- **MuseBeat** (ACM, 2018) — "real-time music generation in sync with heartbeat" ([ACM DL](https://dl.acm.org/doi/10.1145/3170427.3186532)) — title/abstract-level match, worth a follow-up deep dive if the parent project wants more historical precedent, not fully explored here.
- **Harmonic-Melodic-Rhythmic biofeedback MIDI system** (ScienceDirect) — generates MIDI piano-roll representations directly from HRV signals ([ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S1746809421006923)) — another example of the **symbolic-MIDI-first** pattern rather than raw-audio-neural-generation-first.
- **"AI for Generation of Functional Music"** (Frontiers in AI, 2020) — non-linear time series of musical features for "on-the-fly" sound synthesis using perceptually-informed feature similarity ([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC7861294/)) — general precedent for real-time perceptually-driven generative control.

**Section 5 summary verdict:** Every closed-loop/biofeedback system surveyed that achieves reliable rhythmic precision does so by keeping the **clock/grid symbolic and deterministic**, and either (a) using a rule-based symbolic generator for the whole piece (AffectMachine), (b) quantizing all state changes to bar/beat boundaries even when the sound engine is more complex (HEARTBEATS), or (c) accepting looser precision by not reporting/needing exact BPM (MindMelody, using MusicGen with 10-second windows). **No published system asks a raw neural audio model to self-maintain an exact BPM over a long real-time session** — this validates the project's own instinct to decouple symbolic drums from the neural audio bed and enforce alignment externally, rather than seeking a neural fix.

## Synthesis: Recommended Combination

No single technique surveyed delivers exact-BPM, zero-wander, real-time generation on its own. The literature converges on a **layered architecture**:

1. **Reduce drift at the source:** Replace or augment MusicGen with **MusiConGen** (or JASCO) so the generator is conditioned on an explicit symbolic BPM/beat/downbeat signal rather than a text-prompt tempo string — this won't be perfect (~70ms-class tolerance by design) but substantially shrinks the correction needed downstream. ([MusiConGen code](https://github.com/YatingMusic/MusiConGen), [arXiv:2407.15060](https://arxiv.org/html/2407.15060v1))
2. **Guarantee the grid deterministically:** Pipe the generator's output through **Rubber Band** (or `pyrubberband`) time-stretching, computing the exact stretch ratio needed to align the (small, now-reduced) residual drift to the known target BPM/downbeat grid. Because the current wander is small (~127ms), the required stretch ratio will be small, keeping artifacting low. This is the only technique in the survey offering deterministic, exact correction, and it is cheap and mature. ([breakfastquay.com/rubberband](https://breakfastquay.com/rubberband/technical.html))
3. **Solve indefinite extension separately from tempo:** Adopt **LoopGen**'s beat-aware circular-padding inference technique (or track **Live Music Diffusion Models** for a more architecturally advanced streaming solution) to extend the bed seamlessly, aligning loop length to bars so loop boundaries coincide with the downbeat grid already being enforced in step 2. ([LoopGen, arXiv:2504.04466](https://www.arxiv.org/pdf/2504.04466.pdf); [LMDMs, arXiv:2605.22717](https://arxiv.org/html/2605.22717v1))
4. **Adopt the symbolic-clock design lesson from biofeedback literature:** Following **AffectMachine** and **HEARTBEATS**, treat the exact tempo/downbeat grid as an authoritative symbolic clock that is never delegated to the neural model's own sense of time — the neural model (MusicGen/MusiConGen/JASCO) should be treated as a **texture/timbre generator that is corrected into alignment**, not as the timing authority. All parameter/BPM changes from the physiological control signal should be **committed only at bar boundaries** (as HEARTBEATS does), avoiding mid-bar retargeting that would reintroduce audible seams.
5. **(Stretch/future work)** If DITTO-2 code is reimplemented with a custom tempo-matching differentiable loss, it could in principle replace step 1 with something closer to true generative tempo-lock rather than approximate-then-correct — but this is unproven in the literature and represents a real research contribution rather than an off-the-shelf fix, appropriate to flag as a possible novel contribution of the PhD work itself rather than something to expect "for free" from existing papers.

This combination (MusiConGen-style conditioning → Rubber Band exact correction → LoopGen-style seamless extension → symbolic bar-quantized control updates) is assembled entirely from techniques with either public code or well-specified, reproducible algorithms, and is the combination most likely to meet the stated requirement of exact BPM lock with a known downbeat grid in a real-time closed-loop system.
